# 操作日志审计功能 Implementation Plan

> ```markdown
> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> ```

**Goal:** 为二壮系统增加仅系统管理员可访问的操作日志审计页面和后端能力，支持最近 7 天默认查询、最多 3 个月时间范围、操作人/操作类型筛选、分页，以及关键成功/拒绝/失败事件记录。

**Architecture:** 后端通过统一审计记录接口写入 MySQL tb_audit_logs，查询接口在服务端完成权限、时间边界和分页校验。关键写操作在原有事务中追加审计记录，监控/录像/截图等敏感资源在发放前完成审计；前端复用现有系统 token、SystemTopBar、筛选控件、表格和分页样式，不直连数据库。

**Tech Stack:** Go net/http、database/sql、MySQL、React、TypeScript、Vitest。

### Task 2: 实现审计模型、存储和安全过滤

**Files:**
- Create: internal/app/audit_logs.go、internal/app/audit_logs_test.go
- Modify: internal/app/mysql_store.go、internal/app/memory_store.go

- [ ] **Step 1: 定义稳定模型**

增加 AuditLog、AuditLogFilter、AuditLogPage 和 AuditLogStore。AuditLog 至少包含 ID、UserID、ActorDisplayName、UserEmail、Action、EntityType、EntityID、StoreID、ExternalOrgID、ChannelID、IPAddress、UserAgent、RequestID、Result、DetailJSON、CreatedAt；Filter 包含 StartAt、EndAt、UserID、Action、Page、PageSize。

- [ ] **Step 2: 定义查询接口行为**

MySQL 查询必须使用 created_at >= start 和 created_at < end，按 created_at desc、id desc 排序，并用 limit/offset 做服务端分页。Page 最小为 1，PageSize 最大为 100；不接受前端排序字段和 SQL 片段。

```sql
select id, user_id, actor_display_name, user_email, action, entity_type,
       entity_id, store_id, external_org_id, channel_id, ip_address,
       user_agent, request_id, result, detail_json, created_at
from tb_audit_logs
where created_at >= ? and created_at < ?
  and (? is null or user_id = ?)
  and (? = '' or action = ?)
order by created_at desc, id desc
limit ? offset ?
```

- [ ] **Step 3: 建立敏感字段白名单**

sanitizeAuditDetail 只保留业务摘要键；password、token、authorization、wss_url、signed_url、media 等键必须被丢弃。API 响应不返回 detail_json 原文、IP、User-Agent、request ID 或资源签名地址。

- [ ] **Step 4: 补充内存实现和单元测试**

MemoryStore 使用互斥锁保存日志，复制 MySQL 的过滤、排序和分页行为。测试左闭右开时间区间、分页边界、操作类型筛选、敏感字段过滤和空结果。
