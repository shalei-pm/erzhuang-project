# 操作日志审计功能设计

## 1. 背景与目标

在系统设置中增加“操作日志”入口，为系统管理员提供关键操作的审计查询能力。首期支持按时间范围、操作人和操作类型筛选，并展示操作人身份、操作内容和执行结果。

目标是让管理员能够回答：谁在什么时间，对哪个对象执行了什么操作，结果如何。日志不得成为密码、Token、WSS 地址或媒体内容的泄露渠道。

## 2. 范围与角色

- 首期仅系统管理员可以进入操作日志。
- 通过独立权限 `audit.view` 鉴权；当前只授予管理员。
- 审计人员角色只预留设计，不在本期创建、不开放入口。
- 普通用户、编辑运维和运营人员不能查看日志。
- 日志只读，不提供修改、删除、导出或批量清理功能。

## 3. 数据存储

复用项目治理方案中的 `tb_audit_logs`，不新建第二套操作日志表。历史 `tb_operation_logs` 继续承担旧业务摘要记录，不作为本功能的查询来源。

审计表需要保留以下信息：

- `id`：自增审计记录 ID。
- `user_id`：操作人用户 ID，可为空，以保留用户被删除后的历史记录。
- `actor_display_name`：操作当时的“昵称（姓名）”快照。
- `user_email`：操作当时的邮箱快照。
- `action`：稳定的操作编码，例如 `auth.login`、`monitor.live_view`。
- `entity_type`、`entity_id`：操作对象类型和 ID。
- `store_id`、`external_org_id`、`channel_id`：门店、机构和摄像头等业务关联信息，可为空。
- `ip_address`、`user_agent`、`request_id`：审计定位信息。
- `result`：`success`、`denied` 或 `failed`。
- `detail_json`：经过白名单过滤的结构化细节，可为空。
- `created_at`：服务端生成的操作时间。

`detail_json` 禁止写入密码、SSO 凭据、Token、Authorization、WSS URL、签名地址和原始媒体数据。日志查询只返回可展示字段，不返回敏感原始请求内容。

当前仓库已有 `db/mysql_governance_schema_tb.sql` 中的 `tb_audit_logs` 草案，正式执行前由 DBA 在测试库和正式库核对现有表结构并补充 `actor_display_name`。Codex 不直接修改正式数据库。

## 4. 首期记录范围

只记录关键操作，不记录每次普通页面请求、列表翻页或鼠标点击：

| 操作编码 | 展示名称 | 关键对象 |
| --- | --- | --- |
| `auth.login` | 登录 | 当前用户 |
| `auth.logout` | 退出登录 | 当前用户 |
| `monitor.live_view` | 查看监控 | 门店、摄像头 |
| `monitor.playback_view` | 查看录像 | 门店、摄像头、时间范围 |
| `snapshot.download` | 下载截图 | 门店、摄像头 |
| `snapshot.refresh` | 刷新截图 | 门店、摄像头 |
| `user.create` | 新增用户 | 用户 |
| `user.update` | 编辑用户 | 用户 |
| `user.enable` / `user.disable` | 启用/停用用户 | 用户 |
| `user.role_change` | 修改用户角色 | 用户、角色 |
| `user.scope_change` | 修改门店授权范围 | 用户、门店 |
| `store.create` | 新增门店 | 门店 |
| `store.update` | 编辑门店 | 门店 |
| `store.delete` | 删除门店 | 门店 |
| `audit.view` | 查看操作日志 | 日志查询 |

成功、权限拒绝和执行失败的关键操作都记录。登录只在后端确认 SSO 回调成功时记录，不把每次 `auth/me` 查询当作登录。

## 5. 后端接口与写入规则

### 5.1 查询接口

新增管理员专用只读接口：

`GET /api/admin/audit-logs`

请求参数：

- `start_time`：开始时间，必填。
- `end_time`：结束时间，必填；采用左闭右开区间，最大跨度 3 个月。
- `user_id`：可选，操作人筛选。
- `action`：可选，操作类型筛选。
- `page`、`page_size`：分页参数，服务端限制最大页大小。

日期筛选按公司业务时区 `Asia/Shanghai` 解释。页面默认最近 7 天；用户选择范围超过 3 个月时，前端立即提示，后端也必须拒绝，避免绕过页面造成大范围查询。

响应返回 `items`、`page`、`page_size`、`total`，每条记录至少包含：

- 操作人昵称（姓名）
- 邮箱地址
- 操作时间
- 操作类型
- 操作内容摘要
- 操作结果

查询使用服务端分页和时间索引，不允许前端拉取全量日志后筛选。

### 5.2 事件写入

后端建立统一的审计写入接口，事件由请求上下文补齐当前用户、IP、User-Agent 和 request ID。业务服务只提供稳定的 action、对象和安全明细，避免不同 handler 各自拼接日志格式。

- 用户、门店、角色和授权范围变更：审计写入与业务写入使用同一数据库事务；业务失败不写成功日志，审计写入失败则回滚业务变更。
- 监控、录像、截图等敏感读取：在发放播放地址、回放地址或下载响应前完成审计写入；审计写入失败时不发放敏感资源。
- 登录、退出：在后端确认对应成功边界时写入。
- 被拒绝或执行失败：记录结果和安全摘要，不记录凭据或原始错误中的敏感参数。

普通只读页面不依赖审计日志可用性，不因审计表暂时不可用而整体不可浏览。

## 6. 前端页面

入口位于现有“系统设置”菜单中，只有管理员看到“操作日志”。页面采用已确认的静态草稿布局：

- 标题：操作日志。
- 筛选区：操作时间、操作人、操作类型、查询、重置。
- 默认时间：最近 7 天。
- 最大时间范围：3 个月。
- 表格列：操作人、邮箱地址、操作时间、操作类型、操作内容、结果。
- 操作人显示 `昵称（姓名）`，邮箱单独列出。
- 操作内容展示可读摘要，不直接展示 `detail_json`。
- 结果显示成功、拒绝、失败三种状态。
- 支持加载中、无记录、查询失败和无权限状态。
- 不提供日志删除、编辑、导出按钮。

## 7. 安全与错误处理

- 前端不直连数据库；所有查询和写入经过后端鉴权。
- 后端必须同时执行身份认证和 `audit.view` 权限校验。
- 不信任前端传入的操作人姓名、邮箱、结果和操作时间，均由服务端或当前认证上下文生成。
- 审计日志表应用账号只需追加和查询能力；如公司数据库权限允许，应禁止应用删除和更新历史日志。
- 查询参数非法、时间范围超过 3 个月、无权限和数据库异常分别返回明确的 HTTP 错误，不泄露 SQL 或连接信息。
- 首期不自动删除日志；保留周期遵循后续公司安全合规策略，应用暂不提供清理入口。

## 8. 验收标准

1. 管理员登录后能从系统设置进入操作日志；非管理员看不到入口，直接请求接口返回 403。
2. 首次进入默认查询最近 7 天，查询结果按服务端分页返回。
3. 时间范围、操作人、操作类型筛选结果准确；超过 3 个月无法查询。
4. 表格正确显示昵称（姓名）、邮箱、时间、类型、内容和结果。
5. 登录、退出、监控、录像、截图、用户、授权和门店关键操作均能形成记录，成功、拒绝、失败状态正确。
6. 用户资料变更后，历史日志仍显示操作当时的身份快照。
7. 审计写入失败时，关键变更和敏感资源发放不会绕过审计继续成功；普通页面浏览不受影响。
8. 日志、页面、接口响应和错误提示中均不存在密码、Token、Authorization、WSS 地址或原始媒体数据。
9. 前端补充页面状态和筛选测试，后端补充权限、时间边界、分页、事务和敏感字段过滤测试。

## 9. 非目标与后续

- 本期不创建审计人员角色；`audit.view` 为后续扩展保留。
- 本期不做日志导出、删除、归档、报表和告警。
- 本期不记录所有普通浏览行为，不实现行为分析。
- 后续可增加审计人员角色、按门店筛选、CSV 导出、保留周期和日志告警，但需单独评估权限与数据治理。
