# 4.9.0：CRM 机构目录与监控授权统一

## 修复目标

首页已从 CRM 获取机构，而权限配置仍依赖旧门店目录。新机构在 CRM 中出现后，若没有 tb_stores 映射，就无法分配监控权限。本次解除权限候选、保存、回显及鉴权对旧目录的依赖，不再为新增 CRM 机构复制旧门店行。

基线为正式 4.8.5，commit `9f8c14aef8691a8efb76d36df58f327c5b31d176`。本次不包含主开发目录其他尚未提交的数字孪生调整。

## 业务规则

- 权限候选读取启用的 tb_crm_admin_tenant，名称、城市和机构 ID 来自 CRM；不因旧映射、录像机或摄像头暂缺而漏掉候选。
- 首页和权限配置使用同一机构主数据，但列表用途不同：首页保留现有设备能力筛选，权限配置允许预先给启用机构授权。因此两个列表不保证数量完全相同。
- 管理员、编辑运维仍默认全量机构，但实际访问监控也要求该机构在 CRM 中启用。普通查看还须有该机构的显式监控授权。
- 既有停用或暂未同步机构在权限弹窗中保留并标注，可保留、可取消。不能新增不可用机构。停用期间不可查看；再次启用后，未撤销的原授权恢复有效。
- 旧目录停止新增、改名、变更外部机构 ID 和删除，旧导入入口拒绝写入。设计图、区域、录像机、通道、日志及其旧 ID 保留，不删除或重编号。
- 用户确认历史缩略图已删除，故清理旧缩略图回退查询与原图片入口；现行 NVR 截图继续使用原存储与权限。

## 权限协议与存量转换

沿用 tb_user_resource_scopes，不新增表、字段或索引。仓库声明支持 resource_type 为 varchar(32)、resource_id 为 bigint、external_key 为 varchar(128)；本轮未连接实际正式库核查约束、触发器或其他写入者，不能把仓库声明当作生产结构验收。

| 情况 | 行为 |
| --- | --- |
| 旧授权 resource_type=store | 只按已保存 external_key 解释 CRM ID；不按 resource_id 或当前旧目录映射猜测 |
| 新授权 resource_type=crm_institution | resource_id 与规范十进制 external_key 必须同时等于 CRM ID |
| 旧字段 monitor_store_scope_ids 出现 | 整单 409 拒写，包括 null、空数组及新旧字段并存，提示刷新 |
| monitor_institution_ids 缺省或 null | 保留当前授权原样，不转换、不删除、不插入 scope |
| monitor_institution_ids=[] | 明确撤销两种身份的 monitor:view 授权 |
| monitor_institution_ids 为非空数组 | 校验完整目标集合，在同事务内删除两类旧记录，再写完整 CRM 身份集合 |
| 更新任何用户资料、角色或状态 | 必须携带 monitor_scope_revision；用户锁、scope 锁后校验，旧窗口返回 409 |
| CRM 读取失败、异常身份或混合身份 | 明确拒绝，不忽略异常后覆盖、不降级放行 |

revision 包含原始授权元组、角色和启用状态。同类型重复授权回显按 CRM ID 去重；不同类型同时存在视为异常，避免模糊求并集。只接受可由前端安全表达的正整数 ID。

成功审计与权限写入在同事务，记录保留/替换/清空、实际前后数量、新增和撤销的机构 ID。返回内容在提交前准备，避免提交成功后另一次查询失败被误报为保存失败。若 Commit 本身报错，返回 503“提交结果暂时无法确认”，不额外写失败审计；先刷新核对，不盲目重复保存。

## 测试发布与切换

本文件不表示已推送、构建或部署。用户确认测试发布后，按项目发布手册同步 GitHub 备份及 GitLab 测试分支；正式 main 需测试验收后另行授权。

1. 发布窗口暂缓权限编辑，先记录运行版本与回退点。核对实际权限表声明是否兼容，检查其他权限写入者、异常身份和混合身份；发现异常定向复核，禁止自动全量回填。
2. 所有应用实例升级到 4.9.0 后再开放权限编辑，避免旧服务实例继续写 store 类型。刷新旧前端；新后端会拒绝旧协议写入，新前端不会猜测旧 store_id。
3. 在测试环境确认：无旧映射的新 CRM 机构可在权限候选找到，保存后重新打开仍勾选，监控访问与撤销生效；检查机构停用、恢复启用、源查询失败和旧窗口保存冲突。
4. 验证现行 NVR 直播、回放、截图，以及旧设计图等保留数据；这些环境验证不能由本地 fixture 替代。
5. 本地 scripted SQL 测试验证事务调用和回滚分支，不证明真实 InnoDB 双连接锁竞争；上线前在测试库进行双窗口/双请求并发验证，确认撤销后旧窗口不能复活授权。

本轮没有实际正式库连接、生产用户权限写入、表删除或数据迁移。

## 回滚边界

尚未产生非空 CRM 身份授权时，可结合实际写入情况评估代码回退。任一用户保存非空 CRM 身份授权后，4.8.5 不能读取这些授权，不能仅退旧代码并宣称兼容。优先前向修复或回到能读取新身份的兼容版本；确需反向映射时，由 DBA 单独给出逐用户脚本与验证，CRM-only 机构不能凭空创建旧映射。

明确清空的授权必须保持撤销；禁止恢复整表旧快照，以免复活已撤销权限。保留旧表不等于旧代码可以直接回退。旧目录只退出主数据职责，物理删表需另行审计及审批。
