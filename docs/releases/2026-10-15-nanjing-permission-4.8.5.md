# 4.8.5 南京监控权限候选修复

## 原因与修复

原二壮机构资源列表读取 CRM，用户权限候选读取旧 `tb_stores`。测试库只读核查发现：10030 在 CRM 为南京的“数字化测试门店”，旧目录为北京实验室；10053 映射正常；10086 南京金陵中环店没有旧目录映射。因此南京筛选只显示一家。

- 候选名称、城市优先使用 CRM；采用两次批量查询在内存合并，不新增 SQL JOIN，符合公司仓库检查。CRM 缺失、空白或城市未知时保留旧目录显示值。
- 保存及鉴权继续使用原内部 store ID 和 external_org_id，不替换身份、不自动授予权限。
- 每次打开用户编辑/新增弹窗重新请求候选列表，避免永久复用首次加载的缓存。
- 无 DDL、无新字段/索引、不更改实例配置。仅对测试库定向补一条 10086 门店目录。

## 测试库执行结果

- DBA 置顶专项已审核单条补齐方案，以及 RR 事务全主键范围锁替代人工暂停门店写入的方案。
- 执行前确认测试地址 allowlist、InnoDB、无触发器，目录原 71 行；三秒事务预算，任何错误显式回滚。
- 已新增 1 行：机构 10086 → 内部 store ID **900025**，名称“南京金陵中环店”，归一化名称“南京金陵中环”；事务耗时 164ms。
- 原 10030、10053 完整记录与事务内前检相同，本事务用户权限写入为 0。此结论不代表其他并发事务未修改权限。
- 10030 持久字段仍为原北京实验室，不改动门店维护资源含义。
- 正式库未连接、未写入。上述内部 ID 和测试事实不得套用于正式。
