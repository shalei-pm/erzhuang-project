# 4.10.1 倍速诊断（测试发布准备）

用户在测试环境选择4倍速，摄像头画面内时间仍按正常速度推进。真实链路倍速尚未验收通过，不能将模拟服务通过当作公司视频代理已经支持该控制协议。

## 当前控制方式

浏览器取得短期签流地址后，直接连接公司 `/nvrapi/ws`。二壮 Go 服务只申请播放会话，不转发倍速消息。申请参数包含 `camera_id`、`stream_type=2`、回放 `start_time` 和 `end_time`，没有倍率字段。

选择4倍速默认在现有 WebSocket 上发送：

```json
{"sequence":0,"cmd":"speed","rate":4}
```

`sequence` 是递增请求序号，`rate` 为1/2/4/8/16。恢复正常发送 `rate:1`。这个格式沿用提供的 NVRPlayer SDK；其 README 明确注明回放控制需要服务端支持，不能据此确认公司代理的实际实现。

收到服务端 `version:"0.1"` 后，客户端切换为36字节二进制消息，未赋值字节为0，各字段为大端无符号32位整数：偏移0写36、偏移12写命令 `0x0003012F`、偏移32写倍率。尚未获得真实会话使用哪种协议的证据。

当前不通过修改浏览器 `video.playbackRate` 实现加速。帧经解码后绘制到 Canvas，进度取成功绘制帧的媒体 PTS。服务端需让实际录像时间更快推进。客户端用媒体时间增量除以实际时间增量验证；成功回包本身不能证明倍速生效。

## 本轮诊断改动

- 保留控制协议、请求倍率、已验证倍率、可归因回复状态、观测倍率和失败类别。
- 倍速失败后在播放器内提示，并可复制白名单诊断；不含用户信息、摄像头、播放地址、凭据或原始回复。
- 不改变倍速报文或尝试猜测其他协议，保留失败时从当前播放位置重连正常速度的行为。

## 验证与剩余事项

- 前端25文件/260项单测及生产构建通过，仅既有大 chunk 提示。
- 合成服务的拒绝、成功回复但仍1倍两种浏览器场景通过，含手机全屏提示、复制及剪贴板失败降级；不代表真实设备验证通过。
- 调试过程发现开发服务热更新造成测试入口和 React 组件引用不同 SDK 模块，独立新启动 Vite 后回归通过；这属于本地测试环境问题，未据此判定线上根因。
- 尚未取得真实控制回复或视频代理实现证据。需要核对 `/nvrapi/ws` 支持的控制协议、倍速参数及回复格式，是否转换为工控机/NVR控制，以及是否存在设备/录像限制。
- 用户已明确授权将本诊断版发布测试环境。目标为 GitLab `codex/containerize-single-image` / Wharf pipeline `752`，同步 GitHub 功能分支备份；真实部署状态单独核对，不将代码推送视为部署完成。
- 本版不修改正式环境、数据库、视频控制报文或运行配置。回退可在测试环境选择前一镜像 `331b246`（4.10.0），不删除数据。

## 测试操作

1. 确认测试页面实际版本为4.10.1，进入原二壮系统录像回放。
2. 正常播放后选择4倍速，观察画面内摄像头时间是否加快，并等待约6秒。
3. 若倍速失败，点击播放器内失败提示右侧的复制图标，保留诊断信息。剪贴板不可用时，可从展开的文本框取得同一份诊断。
4. `ack=rejected` 表示收到了可归因的拒绝回复；`ack=none` 表示未识别到可归因的确认回复，不等同于服务端未收到消息；`ack=accepted` 且 `observedRate` 约1表示收到了成功回复但媒体仍未按请求倍率推进。
5. 将诊断与画面内时间是否加速一起核对，再决定客户端修复或视频代理协议联调；不以复制成功、ACK成功作为倍速验收通过。
