# Decisions

本文件记录二壮项目的重要产品/技术决策。新的主会话、专项会话、发布会话或评审会话应先读本文件，再读具体实现文档。

## 2026-08-13 二壮 3.0 采用业务库只读门店空间资源查看

- 背景：公司业务库已经维护工控机、NVR、摄像头、诊室/床位和空间-设备绑定关系。二壮继续独立维护门店、录像机、通道识别和空间映射，会造成重复维护、口径分裂和运营成本。
- 结论：
  - 3.0 模块命名为「门店空间资源查看」。
  - 3.0 主流程只读展示公司业务库事实，不在二壮侧新增、编辑、删除或确认门店空间映射。
  - 门店列表只展示有启用工控机的门店。
  - 空间类型使用业务库自己的三层结构：`level=1` 大类、`level=2` 房间/区域、`level=3` 床位/子区域。
  - 详情页展示空间视角、设备视角和异常项，用于检查空间、摄像头、NVR、工控机绑定是否完整。
  - 设计图上传/标注、AI 通道识别、人工确认、门店/录像机/通道写入口在 3.0 主流程隐藏或下线。
  - H5 Monitor 现有查看监控方式保持不变，不在 3.0 改造萤石云播放或工控机/NVR 取流。
- 原因：业务库是设备与空间映射的主数据源，二壮 3.0 更适合作为只读查看和完整性验收入口；监控播放链路已多轮稳定，不应和资源查看大版本同时改造。
- 影响：
  - 需要新增业务库只读连接，推荐环境变量 `BUSINESS_MYSQL_DSN` / `K8S_SECRET_BUSINESS_MYSQL_DSN`，账号必须最小只读权限。
  - 二壮运行库仍负责登录、权限、系统设置和 H5 Monitor；业务库只负责 3.0 资源查看。
  - 旧 storespace/designplan 代码和数据先保留作为回滚与历史兼容，不在 3.0 初期直接删除。
  - 实施前必须给当前 2.x 稳定状态打 tag 或备份分支。
- 文档：
  - 设计：`docs/superpowers/specs/2026-08-13-store-space-resource-view-3-design.md`
  - 计划：`docs/superpowers/plans/2026-08-13-store-space-resource-view-3-implementation.md`

## 2026-07-07 普通查看用户增加查看监控门店范围权限

- 背景：当前普通查看用户拥有 `store:read`，可浏览后台普通页面。用户希望为普通查看用户增加门店级别的“查看监控”范围控制，让业务负责人只看到自己负责门店的监控入口和 H5 Monitor 门店切换范围。
- 结论：
  - 限制对象只针对 `viewer` / 普通查看用户；`admin` 和 `editor` 保持全量。
  - 不限制普通后台页面浏览；普通查看用户仍可浏览普通页面，但没有写入、添加、编辑、删除、扫描、识别、确认等能力。
  - 门店范围只控制监控相关能力：门店详情“查看监控”入口、H5 Monitor 门店切换、直接访问 H5 Monitor URL/API。
  - 授权粒度为门店级别，候选门店为所有有 `external_org_id` 的门店，不按是否已有录像机、设备配置或 H5 Monitor 可用性过滤。
  - 新增普通查看用户默认空范围；空范围允许登录和浏览普通页面，但不能进入任何门店监控。
  - 用户管理交互先做静态 demo，本地确认后再进入生产实现。
- 原因：负责人范围是业务口径，不能和设备配置口径混在一起；后端必须防止普通查看用户通过直接 URL 绕过前端入口限制。
- 影响：第一版应采用前端体验限制 + 后端 H5/API 强校验；数据模型按 scope 化方向设计，优先支持 `store` + `monitor:view`，后续可扩展到城市、机构、资产或更多资源权限。
- 原型：`work/prototypes/viewer-store-scope-demo.html`，当前默认 D 版“城市筛选 + checkbox 门店列表”。A/B/C 保留为备选对照，第一版优先评审 D 版是否够用。

## 2026-07-06 二壮项目停止韩国 Lighthouse 发布链路

- 背景：项目已切换到公司 GitLab/K8s 自动发布链路，运行时数据库和资产存储已迁移为公司 MySQL + OSS。用户确认韩国服务器上关于二壮项目的所有库表已经完全删除。
- 结论：二壮项目后续发布、回滚、验收和排查只走公司 GitLab/K8s，不再使用韩国 Lighthouse/TAT 发布链路。GitHub 的代码备份能力依然保留，作为代码历史和备份，不作为线上发布环境。
- 原因：韩国服务器已不再具备二壮项目的数据基础，继续保留为发布或回滚路径会造成误操作风险，也会误导新会话认为存在可用备用环境。
- 影响：`docs/deploy-runbook.md` 中韩国 Lighthouse/TAT 内容仅保留为历史学习记录；任何“发布到韩国服务器”的请求都应先提示该链路已废止。回滚只能选择仍兼容公司 MySQL/OSS 的公司分支提交。默认仍可同步 GitHub 备份，除非用户明确要求只推公司 GitLab 或不要同步 GitHub。

## 2026-07-04 建立文件化项目记忆机制

- 背景：长期主会话上下文过长，压缩后容易丢失关键状态、线上版本、迁移结论和风险边界。
- 结论：以文件作为项目记忆主载体：
  - `docs/codex-learning-state.md` 保存长期状态、当前进度、运行/部署方式和发布记录。
  - `docs/decisions.md` 保存产品/技术关键决策。
  - `work/current-plan.md` 保存当前轮目标、拆分、进度、验证方式和下一步。
  - `README.md` 和 `docs/technical-architecture-index.md` 作为新会话的项目入口和当前代码地图。
  - `docs/post-cutover-regression-checklist.md` 和 `docs/legacy-postgres-supabase-shutdown-checklist.md` 作为 MySQL/OSS 稳定期的控制清单。
- 原因：文件可被后续会话按需检索，避免只依赖聊天记录；也便于多会话交接。
- 影响：之后每轮需求澄清、开发、测试、发布、回滚或重要讨论后，主会话主动更新项目记忆文件。

## 2026-07-04 公司运行时采用 MySQL + OSS，删除 PostgreSQL 运行时联系

- 背景：公司环境已完成 MySQL/OSS 迁移验收，用户明确公司不希望继续保留与 PostgreSQL/Supabase 的运行时联系，避免数据出海或误连旧库风险。
- 结论：从 `2.30.23` 起，服务运行时只接受 MySQL；删除 pgx 依赖、旧 PostgreSQL repository、旧 schema 初始化、pg-to-mysql 导出 CLI、pg-mysql ops 入口和旧库回滚连接。
- 原因：迁移已经完成，保留旧连接不再是安全阀，反而成为合规和误操作风险。
- 影响：后续回滚不能再依赖切回 PostgreSQL；必须保证 MySQL/OSS 路径自身稳定。旧数据源删除/归档仍需安全/运维/研发确认。
- 版本/提交：`2.30.23`，`338fd1f fix: remove postgres runtime links`。

## 2026-07-06 OpenClaw 摄像头接口只提供只读能力

- 背景：OpenClaw 当前通过在线飞书多维表格读取门店、区域/诊室、录像机和通道映射，未来希望改为读取本系统维护的数据。
- 结论：给 OpenClaw 的接口只提供只读查询能力，不授予后台写权限。
- 原因：OpenClaw 的目标是按门店和区域/诊室找到对应摄像头与截图，不应修改门店、区域、录像机、通道确认或 AI 识别结果，避免外部技能误写核心主数据。
- 影响：方案设计中应优先提供“查询已确认映射”和“读取最近截图”；如需要实时刷新截图，必须单独作为受控能力讨论，因为刷新截图会调用萤石并写入截图台账，具有副作用，不能混入普通只读查询接口。
- 权限口径：建议独立 read-only scope，例如 `openclaw:camera.read` / `store_space.channels.read` / `asset.sensitive.view`，不得复用后台 `editor/admin` 写权限。

## 2026-07-08 OpenClaw 摄像头截图技能暂缓

- 背景：OpenClaw 侧短期无法访问公司外网环境，基于本系统数据支持 OpenClaw 截图的专项调研无法继续形成可验证闭环。
- 结论：暂停 OpenClaw 摄像头截图技能支持工作，归档独立调研会话，不纳入近期主线开发、发布或验收范围。
- 原因：该能力依赖外部技能运行环境和公司网络访问条件；在无法联通验证前继续实现会增加无效代码和权限面。
- 保留口径：未来如恢复推进，仍沿用“只读接口、独立 scope、敏感资产鉴权审计、刷新截图单独讨论”的安全边界。

## 2026-07-06 删除旧 Supabase 前必须先确认请求来源

- 背景：用户准备删除境外 Supabase 数据库，但 Supabase Dashboard 在 Last 60 minutes 仍显示少量请求：Postgres、Storage、Realtime、API Gateway 均有计数。
- 结论：不能仅凭 Dashboard 总请求数判断公司线上仍在访问旧库；删除前必须通过 Supabase Logs、`pg_stat_activity`、K8s Secret/环境变量核查和静默窗口观察确认来源。
- 原因：打开 Supabase 控制台本身可能产生 Postgres / Storage / Realtime / API Gateway 请求；项目代码也仍保留历史资产兼容和迁移工具代码，必须区分“存在代码”与“线上运行时启用”。
- 影响：旧 Supabase/PostgreSQL 删除流程增加一项门槛：确认最近访问来源可解释，且公司运行时没有旧库/旧 Storage 环境变量或 Secret。

## 2026-07-06 旧 Supabase 数据库已删除

- 背景：公司运行时已切换 MySQL + OSS，旧 Supabase/PostgreSQL 不再作为业务运行时或回滚路径；删除前 `pg_stat_activity` 未发现业务服务连接旧库。
- 结论：用户已删除旧 Supabase 数据库。
- 原因：降低境外旧库继续保留带来的数据出海、误连和密钥残留风险。
- 影响：后续任何回滚、调试、数据追溯都不能依赖旧 Supabase/PostgreSQL；必须以 MySQL/OSS、归档备份和线上回归结果为准。删除后需要执行线上健康和核心链路回归。

## 2026-07-04 第 55 家空 external_org_id 门店不迁移

- 背景：用户记忆中共有 55 家门店，但按 `external_org_id` 迁移后 MySQL 有 54 家。审计发现 PostgreSQL 中有 1 家 `external_org_id` 为空的门店：`新氧青春诊所(长沙北辰荟店)`。
- 结论：该门店不纳入本次 MySQL 迁移，当前系统保留 54 家有效机构门店口径。
- 原因：该店缺少机构 ID，可能是被刻意移除、闭店或机构 ID 被复用；强行迁移会破坏按机构 ID 驱动的业务口径。
- 影响：后续统计和验收按“54 家有机构 ID 门店”口径；如业务要求恢复该店，必须先确认机构 ID 和经营状态。

## 2026-07-03 到 2026-07-04 批量通道识别必须节流

- 背景：批量识别多路通道会同步抓图、保存截图、调用 AI，曾触发 APISIX 504 和萤石接口限流/风控。
- 结论：老批量接口 `recognize-channels` 每次最多推进 1 路；页面主流程优先走单通道 `/channels/{channel_id}/recognize`。
- 原因：单次请求保持短、可重试、可观察；避免高频请求萤石接口和 AI 导致整体失败。
- 影响：用户点击批量识别时看起来是少量推进，这是有意设计；失败 2 次后不再自动批量重试，保留人工单通道重试。

## 2026-07-04 AI 非 JSON 输出采用通用兜底

- 背景：MiniMax 和 GPT/OpenAI 类模型都可能在监控截图识别中返回 `<think>` 或解释文本，而不是严格 JSON。
- 结论：通道识别 prompt 禁止输出思考过程；后端对入口、侧门、走廊、通道等非业务画面做文本兜底，低置信并需人工复核。
- 原因：模型返回不可完全控制，非业务画面尤其容易触发解释性输出；直接失败会增加人工重复操作。
- 影响：兜底只能减少失败，不等于高置信自动确认；业务最终仍依赖人工确认。

## 2026-06 到 2026-07 公司环境发布走 GitLab/K8s 固定分支

- 背景：项目从个人练习链路演进到公司环境，需要避免本地目录和公司分支状态分裂。
- 结论：公司发布固定使用 remote `gitlab`、分支 `codex/containerize-single-image`，推送后由公司 GitLab/K8s 自动构建发布。
- 原因：公司环境配置、Dockerfile、运行时变量和 K8s Secret 应由公司链路管理，主会话只负责代码、版本、验证和文档。
- 影响：发布公司环境时禁止 force push，保留公司分支运维配置；推送后等待自动发布并由已登录浏览器验证。

## 2026-06 APISIX SSO 作为公司登录方案

- 背景：公司要求内部系统使用推荐的 APISIX `security-sso` 插件。
- 结论：项目不自建 OAuth2 登录流程，后端校验 `sy_sso_token` RS256 JWT，并用企业邮箱匹配 `tb_users` 授权用户。
- 原因：SSO 负责身份认证，本项目负责授权、角色、权限和页面/接口访问控制。
- 影响：用户不存在或 disabled 时拒绝访问；第一版角色为全局角色，不做机构范围授权。

## 2026-06 第一版后台权限采用全局角色

- 背景：项目需要尽快支持公司内部使用和写接口保护，但机构范围授权会显著扩大设计和验收范围。
- 结论：第一版使用全局角色：`admin`、`editor`、`viewer`；写接口需要 `store:write`，用户管理/AI 设置需要 `user:manage`。
- 原因：先确保接口有真实后端权限守卫，再逐步扩展机构/门店范围。
- 影响：机构范围授权、审计日志、细粒度权限点仍是后续治理任务。

## 2026-06 前端 UI 定位为克制企业后台

- 背景：项目是运营维护工具，不是营销页或展示页。
- 结论：前端按轻量企业后台/SaaS admin 设计，优先稳定信息密度、表格、详情、弹窗、Tab 和明确状态反馈。
- 原因：运营人员会反复使用，需要可扫描、可维护、少装饰的界面。
- 影响：前端改动前必须读取 `docs/ui-standards.md` 和 `docs/frontend-review-checklist.md`，实际浏览器验收不能只看 build。
