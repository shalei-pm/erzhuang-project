# Decisions

本文件记录二壮项目的重要产品/技术决策。新的主会话、专项会话、发布会话或评审会话应先读本文件，再读具体实现文档。

## 2026-08-18 数据库客户端只连测试库，线上 DDL 由运维执行

- 背景：用户确认 TablePro 可以直接访问测试库；线上库出于安全原因不允许本机客户端直连，只能由线上代码或公司批准链路访问。测试库与线上库当前按结构一致口径管理。
- 结论：
  - 本机 TablePro 只用于连接测试库 `polar-dev.rwlb.rds.aliyuncs.com:3306/db_pm_erzhuang`，用于开发验证、只读排查和表结构核对。
  - 线上库 `polar-ops.rwlb.rds.aliyuncs.com:3306/db_pm_erzhuang` 不通过 TablePro、本机 CLI 或 Codex 本机脚本直连。
  - 涉及线上表结构变更时，主会话/DBA 专项产出 SQL、影响说明、验证 SQL 和回滚建议，由用户提交给运维执行。
  - 数据库密码、完整 DSN 和其他密钥不得写入仓库、文档、命令行、长期连接配置或最终回复。
  - 2026-08-18 已在测试库只读确认四张资源查看表均存在且有数据；用户确认线上二壮库也已同步。3.0 应收敛为读取项目主库连接，不继续依赖独立业务库 DSN。
- 原因：兼顾开发效率和线上数据库安全边界，避免 Codex 或本机工具直接接触线上库，同时保证线上 DDL 变更可审查、可追溯、可回滚。
- 影响：以后排查“测试有数据/线上没数据”时必须区分客户端测试结果与线上代码链路验证结果；上线前验收需要同时看测试 TablePro 结果、线上健康检查和线上 API/页面结果。

## 2026-08-14 公司测试环境与线上环境严格隔离

- 背景：研发侧约定 `*.sy.soyoung.com` 默认是内网可见测试环境；二壮测试地址和线上地址虽然路径同为 `/erzhuang-project`，但背后对接的代码分支、实例机器和数据库不同。
- 结论：
  - GitLab 仓库不变：`https://gitlab.sy.soyoung.com/pm/shalei-pm/erzhuang-project.git`。
  - 测试入口为 `https://lite.sy.soyoung.com/erzhuang-project`，对接测试分支 `codex/containerize-single-image`、测试实例机器和测试数据库，Wharf pipeline 为 `752`。
  - 线上入口为 `http://lite.soyoung.com/erzhuang-project`，对接 GitLab `main`、主干实例机器和线上数据库，Wharf pipeline 为 `771`。
  - 2026-08-14 起项目目标从历史测试环境发布切到公司正式环境发布；正式环境是在 `main` 分支提交代码后自动触发 pipeline `771` 构建，构建成功后需要在 Wharf 点部署并走审批，审批通过并部署成功才算上线完成。
  - 主会话说“发布到公司”时，必须先确认测试还是正式。正式发布需要确认线上实例配置、线上数据库、SSO/网关、回滚点、构建状态、审批状态、部署结果和验收清单。
  - 二壮运行库测试环境为 `polar-dev.rwlb.rds.aliyuncs.com:3306/db_pm_erzhuang`，正式环境为 `polar-ops.rwlb.rds.aliyuncs.com:3306/db_pm_erzhuang`，用户为 `u_pm_erzhuang_rw`；密码只通过 K8s Secret 或安全渠道管理，不写入仓库或文档。
- 原因：避免把测试分支自动发布误认为生产发布，避免测试数据库和线上数据库混用。
- 影响：后续域名、SSO、Cookie、网关、回调地址和部署验证都要区分测试与线上；尤其前端公司域名判断需要同时考虑 `lite.sy.soyoung.com` 和 `lite.soyoung.com`，但线上发布流程不能复用测试分支假设。

## 2026-08-13 二壮 3.0 采用业务库只读门店空间资源查看

- 背景：公司业务库已经维护工控机、NVR、摄像头、诊室/床位和空间-设备绑定关系。二壮继续独立维护门店、录像机、通道识别和空间映射，会造成重复维护、口径分裂和运营成本。
- 结论：
  - 3.0 模块命名为「门店空间资源查看」。
  - 3.0 主流程只读展示公司业务库事实，不在二壮侧新增、编辑、删除或确认门店空间映射。
  - 门店列表只展示有启用工控机的门店。
  - 空间类型使用业务库自己的三层结构：`level=1` 大类、`level=2` 房间/区域、`level=3` 床位/子区域。
  - 详情页展示空间视角、设备视角和异常项，用于检查空间、摄像头、NVR、工控机绑定是否完整。
  - 设计图上传/标注、AI 通道识别、人工确认、门店/录像机/通道写入口在 3.0 主流程隐藏或下线。
  - H5 Monitor 现有查看监控方式保持不变，不在 3.0 改造萤石云播放或工控机/NVR 取流。
- 原因：业务库是设备与空间映射的主数据源，二壮 3.0 更适合作为只读查看和完整性验收入口；监控播放链路已多轮稳定，不应和资源查看大版本同时改造。
- 影响：
  - 历史初版曾使用独立业务库只读连接；该连接方案已被 2026-08-18「3.0 资源查看收敛到二壮主库只读查询」决策替代。
  - 二壮运行库仍负责登录、权限、系统设置和 H5 Monitor；业务库只负责 3.0 资源查看。
  - 旧 storespace/designplan 代码和数据先保留作为回滚与历史兼容，不在 3.0 初期直接删除。
  - 实施前必须给当前 2.x 稳定状态打 tag 或备份分支。
- 文档：
  - 设计：`docs/superpowers/specs/2026-08-13-store-space-resource-view-3-design.md`
  - 计划：`docs/superpowers/plans/2026-08-13-store-space-resource-view-3-implementation.md`

## 2026-08-18 3.0 首页保留映射覆盖统计，不展示异常汇总

- 背景：用户确认首页的“摄像头、已绑定、未绑定”可用于快速检查映射覆盖率；“空间”暂时按三层空间节点总数展示。异常项是详细排查信息，同一设备可能产生多项，因此不适合首页汇总呈现。
- 结论：
  - 首页保留摄像头总数、空间总数、已绑定摄像头数、未绑定摄像头数。
  - 首页移除顶部“异常”统计和表格“异常”列。
  - 异常计算、API 字段和详情页“异常项”保留，不改变数据质量排查能力。
  - 空间统计暂时保持三级节点总数，后续根据业务定义再调整。
- 原因：首页的主要任务是浏览门店资源覆盖率；异常项不具备一条记录对应一个问题设备的稳定语义，放在详情页更符合排查流程。
- 影响：前端首页不再消费 `warningCount` 做展示；后端不删除该字段，避免损失详情和后续扩展能力。

## 2026-08-18 空间与摄像头绑定以 `tb_crm_iot_area_device_relation` 为准

- 背景：业务库维护研发确认，`tb_crm_consulting_room` 的房间/床位并不直接含摄像头字段，而是经由 `tb_crm_iot_area_device_relation` 与 `tb_crm_iot_device` 中 `category='camera'` 的设备关联。
- 结论：
  - `area_id` 对应 `tb_crm_consulting_room.id`，`device_id` 对应 `tb_crm_iot_device.id`；展示摄像头绑定时才筛设备 `category='camera'`，不假定关系表只含摄像头。
  - 这是 3.0 展示“空间/床位 -> 设备 -> 摄像头/NVR/工控机”关系的权威来源；二壮不另建映射表、不人工维护副本。
  - 唯一约束为 `(device_id, area_id, function_type)`；`function_type` 必须作为绑定用途保留，未确认业务枚举前不作为过滤条件。
  - 当前测试 `db_pm_erzhuang` 尚未同步该表，3.0 不能据此声称映射完整；须由运维同步到测试和线上二壮库后再做覆盖率验收。
- 原因：把映射主数据收敛在业务库，避免二壮与业务系统出现双写和口径漂移，同时不丢失同一设备、空间在不同用途下的合法多重关系。
- 影响：资源详情查询、异常计算和绑定数统计需按三字段唯一性建模；上线前需要验收关系表行数、`function_type` 分布、摄像头关联数和孤儿 `area_id`/`device_id`。

## 2026-08-18 3.0 资源查看收敛到二壮主库只读查询

- 背景：测试 `db_pm_erzhuang` 已核实具备 `tb_crm_admin_tenant`、`tb_crm_iot_device`、`tb_crm_consulting_room`、`tb_crm_iot_area_device_relation` 四张资源查看表；用户确认线上二壮库也已同步。继续维护第二条业务库 DSN 会增加网络、密钥和部署失败面。
- 结论：3.0 资源查看改为复用二壮项目主 MySQL 连接，但 repository 与 API 均保持严格只读，不向同步表或其他业务表写入任何数据。
- 原因：数据已经按安全要求复制到项目所属库，复用主库能避免跨库网络隔离、额外 Secret 和启动降级复杂度，同时不改变业务库作为原始主数据来源的治理口径。
- 影响：需要删除独立 `BUSINESS_MYSQL_DSN` / `K8S_SECRET_BUSINESS_MYSQL_DSN` 的代码和部署依赖，改动后重新做真实数据 API、前端和正式环境验证。线上同步结果通过正式应用 API 验证，不以本机直连替代。

## 2026-08-13 3.0 业务库只读连接失败时主系统降级运行

- 背景：3.0 新增公司业务库只读连接后，首次发布曾因业务库连接失败导致 Pod BackOff；随后 3.0.2 测试环境确认代码与 Secret 已生效，但业务库 MySQL 握手读取超时，资源查看 API 返回 `resource_view_not_configured`。2026-08-14 用户补充确认：此前使用的是公司测试环境，而目标业务库表必须在正式环境才能访问，因此测试环境无法访问该库表属于环境隔离导致的预期现象。
- 结论：
  - 业务库只读连接是 3.0「门店空间资源查看」的必要依赖，但不是二壮主系统、登录、系统设置和既有 H5 Monitor 的启动必要依赖。
  - 启动阶段业务库连接失败时，主系统继续运行，资源查看 API 返回清晰未配置错误，并通过容器日志记录失败原因。
  - 3.0 正式可用门槛必须包含正式 K8s/正式实例到正式业务库 RDS 的 MySQL 协议握手和 `select 1` 验收，不能只看测试环境 Secret 是否存在或 3306 TCP 端口是否 open。
- 原因：新只读资源页不应拖垮已稳定的后台和监控能力；但只读连接未真正可用时，也不能假装资源页已完成。
- 影响：后续排查 `resource_view_not_configured` 时优先确认当前是测试还是正式环境。测试环境访问正式业务库失败不视为代码 bug；正式环境若仍出现 `context deadline exceeded` 或 MySQL `i/o timeout`，再交由运维/DBA 查 RDS 白名单、安全组、VPC、代理链路或账号连接策略，代码侧不应盲目改 SQL。

## 2026-07-07 普通查看用户增加查看监控门店范围权限

- 背景：当前普通查看用户拥有 `store:read`，可浏览后台普通页面。用户希望为普通查看用户增加门店级别的“查看监控”范围控制，让业务负责人只看到自己负责门店的监控入口和 H5 Monitor 门店切换范围。
- 结论：
  - 限制对象只针对 `viewer` / 普通查看用户；`admin` 和 `editor` 保持全量。
  - 不限制普通后台页面浏览；普通查看用户仍可浏览普通页面，但没有写入、添加、编辑、删除、扫描、识别、确认等能力。
  - 门店范围只控制监控相关能力：门店详情“查看监控”入口、H5 Monitor 门店切换、直接访问 H5 Monitor URL/API。
  - 授权粒度为门店级别，候选门店为所有有 `external_org_id` 的门店，不按是否已有录像机、设备配置或 H5 Monitor 可用性过滤。
  - 新增普通查看用户默认空范围；空范围允许登录和浏览普通页面，但不能进入任何门店监控。
  - 用户管理交互先做静态 demo，本地确认后再进入生产实现。
- 原因：负责人范围是业务口径，不能和设备配置口径混在一起；后端必须防止普通查看用户通过直接 URL 绕过前端入口限制。
- 影响：第一版应采用前端体验限制 + 后端 H5/API 强校验；数据模型按 scope 化方向设计，优先支持 `store` + `monitor:view`，后续可扩展到城市、机构、资产或更多资源权限。
- 原型：`work/prototypes/viewer-store-scope-demo.html`，当前默认 D 版“城市筛选 + checkbox 门店列表”。A/B/C 保留为备选对照，第一版优先评审 D 版是否够用。

## 2026-07-06 二壮项目停止韩国 Lighthouse 发布链路

- 背景：项目已切换到公司 GitLab/K8s 自动发布链路，运行时数据库和资产存储已迁移为公司 MySQL + OSS。用户确认韩国服务器上关于二壮项目的所有库表已经完全删除。

## 2026-07-04 公司运行时采用 MySQL + OSS，删除 PostgreSQL 运行时联系

- 背景：公司环境已完成 MySQL/OSS 迁移验收，用户明确公司不希望继续保留与 PostgreSQL/Supabase 的运行时联系，避免数据出海或误连旧库风险。
- 结论：从 `2.30.23` 起，服务运行时只接受 MySQL；删除 pgx 依赖、旧 PostgreSQL repository、旧 schema 初始化、pg-to-mysql 导出 CLI、pg-mysql ops 入口和旧库回滚连接。
- 原因：迁移已经完成，保留旧连接不再是安全阀，反而成为合规和误操作风险。
- 影响：后续回滚不能再依赖切回 PostgreSQL；必须保证 MySQL/OSS 路径自身稳定。旧数据源删除/归档仍需安全/运维/研发确认。
- 版本/提交：`2.30.23`，`338fd1f fix: remove postgres runtime links`。

## 2026-07-06 OpenClaw 摄像头接口只提供只读能力

- 背景：OpenClaw 当前通过在线飞书多维表格读取门店、区域/诊室、录像机和通道映射，未来希望改为读取本系统维护的数据。
- 结论：给 OpenClaw 的接口只提供只读查询能力，不授予后台写权限。
- 原因：OpenClaw 的目标是按门店和区域/诊室找到对应摄像头与截图，不应修改门店、区域、录像机、通道确认或 AI 识别结果，避免外部技能误写核心主数据。
- 影响：方案设计中应优先提供“查询已确认映射”和“读取最近截图”；如需要实时刷新截图，必须单独作为受控能力讨论，因为刷新截图会调用萤石并写入截图台账，具有副作用，不能混入普通只读查询接口。
- 权限口径：建议独立 read-only scope，例如 `openclaw:camera.read` / `store_space.channels.read` / `asset.sensitive.view`，不得复用后台 `editor/admin` 写权限。

## 2026-07-08 OpenClaw 摄像头截图技能暂缓

- 背景：OpenClaw 侧短期无法访问公司外网环境，基于本系统数据支持 OpenClaw 截图的专项调研无法继续形成可验证闭环。
- 结论：暂停 OpenClaw 摄像头截图技能支持工作，归档独立调研会话，不纳入近期主线开发、发布或验收范围。
- 原因：该能力依赖外部技能运行环境和公司网络访问条件；在无法联通验证前继续实现会增加无效代码和权限面。
- 保留口径：未来如恢复推进，仍沿用“只读接口、独立 scope、敏感资产鉴权审计、刷新截图单独讨论”的安全边界。

- 背景：MiniMax 和 GPT/OpenAI 类模型都可能在监控截图识别中返回 `<think>` 或解释文本，而不是严格 JSON。

- 原因：模型返回不可完全控制，非业务画面尤其容易触发解释性输出；直接失败会增加人工重复操作。
- 影响：兜底只能减少失败，不等于高置信自动确认；业务最终仍依赖人工确认。

## 2026-08-20 新工控机 WSS 取流不以萤石官方播放器替换为前提

- 背景：10001 灰度的新工控机取流链路根据空间关系找到 `camera_id` 后由鉴权服务签发短时 token，再连接公司 WSS。用户提供了与该链路配套的 `NVRPlayer-SDK`，同时希望优先评估萤石/海康官方播放器及移动端兼容性。
- 结论：当前不选定播放器、不接入代码。现有萤石官方播放器仅适用于 FLV、HLS/m3u8 或萤石 `ezopen` 协议，不能直接解码公司 WSS 的 RTP/H.265 与海康私有回放封装。若工控机服务能提供受控 HLS/FLV/WebRTC 输出，优先重新评估官方 SDK；若只能提供当前 WSS 协议，则以 NVRPlayer 的实现作为协议适配参考，但必须完成安全、移动端和维护收口后才可灰度。
- 原因：播放器的协议兼容性由输入媒体封装决定，而不是品牌相同即可互换。强行将 WSS 交给 ezuikit-flv/HLS 会失败；直接复制当前 SDK 又会留下 token 日志、过期 URL 自动重连、预发 CDN 依赖和 iOS 直播不可用等风险。
- 影响：二壮后端仍负责鉴权、门店范围授权、空间到摄像头映射、短时地址签发与审计；浏览器不持有长期鉴权凭据。实施前必须取得正式 `wsUrl` 下发接口、协议文档、录像分段/回放/释放语义及移动端验收范围。当前不修改旧萤石链路。

## 2026-08-20 工控机直播首期必须支持 iPhone 与微信内打开

- 背景：用户明确 iPhone/微信内打开直播是新取流能力的基础要求，不是后续优化项。
- 结论：不接受仅依赖 H.265 WebCodecs 的桌面方案作为首期正式实现。当前 NVRPlayer 可用于验证私有 WSS 协议和桌面 Chrome/Edge，但不得作为 iOS 兼容性的承诺。工控机/NVR 当前无法输出 HLS、FLV 或 WebRTC，因此首期先用独立实验页验证两条路径：浏览器端 RTP/H.265 解析后接入跨浏览器 WASM 软解器；或独立软件网关从既有 WSS 取流并转为 iOS 可播放格式。未经真机验证，不承诺任一路径可用。
- 原因：iOS 所有浏览器与微信内核均受 WebKit 能力限制，H.265 WebCodecs 不是可稳定依赖的基础能力；而要求硬件增加标准输出已被接口方明确否决。兼容层只能由浏览器软件解码或额外软件网关承担。

## 2026-08-26 NVR 回放复用 2.x 播放器进度拖动

- 背景：NVR 回放已能按固定小时窗口创建会话，但缺少 2.x 录像模式已有的片段内进度拖动。
- 结论：复用 `PlaybackSegmentSlider` 作为播放器控制栏中央的回放定位控件。页面底栏继续只切换实时视频和录像；当前小时窗口提供 slider 的起止范围。
- 原因：进度定位是播放器内的回放操作，2.x 也在相同位置呈现。抽取 slider 的最小时间范围类型后，旧萤石录像片段和 NVR 小时窗口可以共享交互与样式。
- 行为与限制：拖动松开后，以目标秒和原窗口结束时间重新签发 NVR 回放会话。NVR SDK 未提供可靠媒体时间码，游标仅在首帧后按播放/暂停状态做秒级估算，最终播放位置以新会话实际返回流为准。

## 2026-08-26 NVR 回放窗口与会话起点分离

- 背景：3.1.12 将拖动目标写入滑块窗口起点，导致会话重建后滑块按缩短区间重算为零或错误比例。
- 结论：小时窗口是用户选择的固定进度参照，整个回放过程中不可因定位而变化；每次 WSS 会话仅记录实际请求的起止时间。
- 原因：2.x 的片段边界与播放 URL 的起点本来就是两套状态。保持边界稳定才能让滑块位置始终代表用户在原小时中的绝对比例。
- 验收：发布后至少验证中段和末段定位，确认会话请求从目标秒开始、滑块不归零、首帧恢复后游标继续推进。

## 2026-08-26 NVR 缩略图采用一次性后端回填，而非页面功能或定时服务

- 背景：NVR 摄像头列表需要默认缩略图，但目前没有工控机静态截图接口。用户不接受常驻浏览器队列、单摄像头人工维护、Web 实例新配置或周期性刷新。
- 结论：使用独立的一次性后端 Job，严格串行处理符合 `camera + HikVisionNvrChannel + status=1 + not deleted` 口径的摄像头。Job 读 `tb_crm_*`，只写私有 OSS 与二壮自有表 `tb_nvr_camera_snapshots`；Web 只做权限受控读取，优先新图、再回退既有安全旧图、最后显示灰色占位。
- 原因：将高风险媒体抓取与常驻 Web 服务隔离，避免业务用户操作、周期成本和错误映射；已完成的条目可由数据库状态续跑。
- 前置：表结构由 DBA/运维在测试和正式库执行；先以测试 `10001` 单个已知可直播摄像头验证服务端 WSS/RTP/H.265 到 ffmpeg JPEG。技术闸门未通过前，不进行 44 路或全量批处理。
- 日期：2026-08-26

## 2026-08-26 NVR 缩略图数据模型经直属 DBA 评审后定稿

- 背景：主会话直属 DBA 子 agent 已对回填 DDL、最小权限和回滚做只读评审。
- 结论：以业务摄像头全局主键 `camera_id` 作为唯一键，保留 `tenant_id` 用于机构查询与校验；OSS 对象 Key 使用 `ascii_bin`，不保存完整 URL；不建立到同步 `tb_crm_*` 表的外键。保留 `status`、`attempted_at`、`error_code`，以支持失败分类和显式续跑，但不保存上游错误全文。
- 原因：摄像头 ID 本身全局唯一，外键会把自有数据与同步表生命周期耦合；对象 Key 需要二进制一致的比较；没有失败状态将无法做到安全、可审计的分批恢复。
- 执行边界：先做不写 MySQL/OSS 的单摄像头解码技术闸门；通过后由运维在测试库执行 DDL，并为独立 Job 配置最小读写权限。Web 服务没有 DDL、回填写入或 NVR 鉴权 Secret 权限。
- 日期：2026-08-26

## 2026-08-26 NVR 缩略图先以无副作用命令验证服务端解码

- 背景：浏览器已证明 NVRPlayer 能播放工控机 WSS 流，但服务端能否从同一 RTP/H.265 流可靠产生 JPEG 仍是批量初始化的技术未知。
- 结论：先使用独立 `nvr-snapshot-spike` 容器做单摄像头直播技术验证。命令不读取或写入 MySQL/OSS，不创建文件，不修改 Web 服务，只在内存中完成“签发短期 WSS -> 解 RTP/H.265 -> ffmpeg JPEG”。它只接受一个正数 `camera-id`，端到端最大 20 秒。
- 原因：先把媒体协议兼容性与 DDL、对象存储、队列和批处理风险解耦。若该闸门失败，立即停止后续回填工作，不在业务数据侧制造半成品。
- 安全：命令和日志的成功输出仅含摄像头 ID、图片元数据和字节数；失败输出仅含摄像头 ID、稳定错误码。Authorization、JWT、WSS URL、上游错误正文和媒体内容只存在于进程内存，不写日志或持久化。
- 发布边界：本命令及独立镜像仅可先同步 GitHub 备份，不得推 GitLab、触发 Wharf 或运行测试环境，直到用户明确批准 `10001` 单摄像头无副作用验证。
- 日期：2026-08-26
