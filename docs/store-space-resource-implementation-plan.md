# 门店空间资源管理系统实施计划

最后更新：2026-06-11

版本：v0.1 正式草案

## 1. 交付目标

在现有 `erzhuang-project` 内完成门店空间资源管理系统第一版。

第一版必须可用，目标是：

- 门店可以通过设计图或录像机任一入口创建。
- 设计图可以维护业务区域和图纸标注。
- 录像机可以真实调用萤石云 API 扫描有效通道。
- 通道可以抓图并通过 AI 识别预填区域类型和编号。
- 用户可以人工确认通道与业务区域映射。
- 区域主数据可以同时被设计图和通道映射引用。

## 2. 开发组织方式

继续采用主架构会话 + 专项会话模式。

主架构会话职责：

- 产品范围确认。
- 技术方案和数据模型决策。
- 分支任务拆分。
- PR review 和合并判断。
- 发布、验证和回滚。
- 腾讯云、nginx、systemd、Supabase、萤石云密钥和 AI key 管理。

前端专项会话职责：

- React 页面改造。
- 组件拆分。
- 设计图 Tab 适配。
- 通道映射 Tab。
- 账号配置 UI。
- 前端构建验证。

后端专项会话职责：

- Go 数据模型。
- PostgreSQL schema。
- 门店/区域/录像机/通道 API。
- 萤石云 client。
- AI 识别 adapter。
- 后端测试。

部署发布仍只由主架构会话执行。

## 3. 分支策略

常规开发走分支和 PR。

建议分支：

```text
codex/store-space-backend-foundation
codex/store-space-frontend-shell
codex/store-space-ezviz-integration
codex/store-space-design-plan-adapter
codex/store-space-video-recognition
```

每个分支要求：

- 小范围职责。
- 有文档或状态记录。
- 提交前检查无密钥、无本地构建产物。
- 合并前由主架构会话 review。

## 4. 阶段拆分

### Phase 0：文档和架构确认

目标：

- 完成 PRD、技术方案、实施计划。
- 用户大模块确认。

交付：

- `docs/store-space-resource-prd.md`
- `docs/store-space-resource-tech-plan.md`
- `docs/store-space-resource-implementation-plan.md`

验收：

- 用户确认整体范围。
- 明确第一版真实接入萤石云和 AI。

### Phase 1：后端基础数据模型

目标：

- 新增通用门店、区域、设计图标注、萤石云账号、录像机、通道、截图表。
- 保持现有设计图模块线上可用。

任务：

- 新增 `internal/storespace`。
- 新增 schema 初始化。
- 新增 RLS 和显式拒绝 policy。
- 新增门店列表 API。
- 新增门店详情 API。
- 新增添加门店 API。
- 新增删除门店 API。
- 新增区域主数据服务。
- 新增录像机唯一校验。
- 新增基础测试。

验收：

- 可创建只有设计图的门店。
- 可创建只有录像机的门店。
- 可创建同时包含设计图和多台录像机的门店。
- 只填门店名称创建失败。
- 单门店最多 3 台录像机。
- 设备编码全系统唯一。
- `go test ./...` 在服务器通过。

### Phase 2：前端骨架和页面改造

目标：

- 在不破坏现有图纸体验的前提下，改造门店列表、添加门店浮层和门店详情。

任务：

- 拆分 `frontend/src/App.tsx`。
- 新增添加门店浮层。
- 新增门店详情页面。
- 新增两个 Tab：设计图标注、通道映射。
- 门店列表字段改造。
- 接入新门店 API。
- 保留页面底部版本号。

验收：

- 门店列表展示新字段。
- 添加门店支持设计图和最多 3 个录像机输入框。
- 创建后自动进入正确 Tab。
- 老的设计图查看和标注体验基本保留。
- `tsc -b` 和 `vite build` 通过。

### Phase 3：设计图模块适配区域主数据

目标：

- 设计图不再作为区域唯一来源。
- 图纸识别和手工标注读写通用区域主数据。

任务：

- 上传设计图后不自动识别。
- 用户手动触发图纸识别。
- 图纸识别结果按“区域类型 + 编号”匹配已有区域。
- 未匹配结果作为候选，确认后生成正式区域。
- 已有业务区域未标注时，在图纸上生成待确认占位框。
- 设计图状态计算。

验收：

- 通道先生成的区域，可以在图纸 Tab 中看到待标注框。
- 图纸识别到已有区域时能自动匹配。
- 图纸识别到新业务区域时，确认后生成区域。
- 设计图状态从待标注变为已完成。

### Phase 4：萤石云账号和录像机扫描

目标：

- 真实接入萤石云账号和录像机扫描。

任务：

- 新增萤石云账号配置 API。
- 新增账号配置 UI。
- 新增 `internal/ezviz` client。
- 新增录像机扫描 API。
- 实现设备在线/离线判断。
- 实现有效通道扫描。
- 重新扫描时保留仍有效通道确认结果。
- 失效通道标记 inactive 并隐藏。

验收：

- 可配置多个萤石云账号。
- 添加录像机时可选择账号。
- 设备不存在或无权限时，录像机离线。
- 单台录像机可扫描有效通道。
- 有效通道数量正确展示。

依赖用户提供：

- 萤石云账号名。
- appKey。
- appSecret。
- accessToken。
- 测试录像机设备编码。

### Phase 5：通道抓图和 AI 识别

目标：

- 真实抓取通道截图并 AI 识别。

任务：

- 单通道抓图。
- 缩略图和大图保存。
- 大图一周过期字段。
- 单台录像机队列式识别全部通道。
- 单通道重新识别。
- 失败重试 3 次。
- 识别失败状态。
- AI 输出 JSON schema。
- 非业务画面类型支持。
- 编号纸提示。

验收：

- 通道列表展示缩略图。
- 点击缩略图可看大图。
- 单台录像机识别时展示进度。
- 失败通道最多重试 3 次。
- AI 结果只预填，不自动生效。
- 用户确认后才生成或绑定区域。

依赖用户提供：

- AI 接口 key。
- 模型或接口形式。

### Phase 6：状态、校验和发布验收

目标：

- 完成第一版状态闭环和线上验收。

任务：

- 设计图状态计算。
- 录像机数量和有效通道数量统计。
- 三类业务区域数量统计。
- 门店完善状态计算。
- 删除保护和二次确认。
- 操作日志。
- 上线前回归。
- 发布记录。

验收：

- 门店列表统计准确。
- 通道映射完成标准正确。
- 设计图完成标准正确。
- 门店已完善标准正确。
- 删除门店清理全部关联数据。
- 已被引用区域不能直接删除。
- 线上版本号可见。
- 可回滚。

1. 文档确认：PRD + 技术方案 + 实施计划。
2. 后端基础模型确认：能创建门店、区域、录像机、通道基础数据。
3. 前端页面骨架确认：列表、添加门店、详情两个 Tab。
4. 设计图适配确认：现有体验保留，区域主数据适配成功。
5. 萤石云扫描确认：真实账号和录像机扫描成功。
6. 通道 AI 识别确认：抓图、识别、确认、生成区域闭环。
7. 第一版上线验收：完整流程跑通。

## 6. 验收主流程

### 流程 A：只有设计图

1. 添加门店。
2. 填门店名称。
3. 上传设计图。
4. 创建成功进入设计图标注 Tab。
5. 点击识别图纸区域。
6. 确认或修正区域。
7. 保存标注。
8. 门店列表显示区域数量。

### 流程 B：只有录像机

1. 添加门店。
2. 填门店名称。
3. 选择萤石云账号。
4. 填录像机设备编码。
5. 创建成功进入通道映射 Tab。
6. 扫描该录像机。
7. 识别本录像机全部通道。
8. 人工确认业务区域或非业务画面。
9. 门店生成区域主数据。
10. 设计图 Tab 显示待上传或待标注。

### 流程 C：录像机反推设计图

1. 通道映射已确认治疗室 1、面诊室 2。
2. 后续上传设计图。
3. 图纸 Tab 自动显示已有业务区域的待标注占位框。
4. 用户拖动矩形框到正确位置并确认。
5. 设计图状态变为已完成。

### 流程 D：设计图反推通道

1. 图纸已确认面诊室 1、治疗室 2。
2. 通道扫描识别出面诊室 1。
3. 用户确认后自动绑定已有面诊室 1。
4. 治疗室 2 如果没有通道，后续校验可提示未绑定摄像头。

## 8. 风险和缓解

### 8.1 数据模型迁移风险

风险：

- 现有 `design_plan_*` 表和新 `store_*` 表需要兼容。

缓解：

- 第一阶段新增表和适配层，不立即删除旧表。
- 数据迁移单独做。

### 8.2 萤石云 API 不确定

风险：

- 接口字段、token 刷新、通道有效性定义可能和预期不同。

缓解：

- 先用测试账号和测试录像机做 Spike。
- 把 API client 封装在 `internal/ezviz`。

### 8.3 AI 识别不稳定

风险：

- 编号纸不清晰、画面遮挡、截图模糊导致识别失败。

缓解：

- 队列识别。
- 单通道重试 3 次。
- 用户可重新识别和人工确认。

### 8.4 前端复杂度上升

风险：

- 继续堆在 `App.tsx` 会难以维护。

缓解：

- Phase 2 先做组件拆分。
- 复用现有设计 token 和图纸组件。

## 9. 第一版完成定义

第一版完成必须满足：

- 用户可以创建门店。
- 用户可以通过设计图或录像机至少一种方式建立区域主数据。
- 真实萤石云扫描可用。
- 真实 AI 通道截图识别可用。
- 用户可以人工确认通道映射。
- 图纸和通道能围绕同一套业务区域工作。
- 线上发布成功。
- 有发布记录和回滚方案。
