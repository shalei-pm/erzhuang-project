# NVR 回放倍速联查材料

日期：2026-11-17。仅测试链路复现；没有发布正式环境，没有修改设备配置或数据库。

## 需要解决的问题

原二壮监控录像回放需要 2/4/8/16 倍、暂停续播、恢复普通和快进 10 秒。二壮已修复客户端自动回普通速度及解码滞后，但完整交付仍被两个真实录像问题阻塞。下述问题在用户提供的原 SDK 上也能复现。

## 可复现输入

- 公司测试入口，机构 10001（北京保利总部店），摄像头 103（机房）。
- 录像窗口：2026-11-17 10:00:00–11:00:00，北京时间。录像保留期之外请换同设备有完整录像的窗口重新验证。
- 正常速度先确认画面时间在 10:00 附近，再调用原 SDK `player.setSpeed(2)` 或 `player.setSpeed(16)`。
- 同一时间只保留一条该回放连接。WebSocket 经现有授权接口实时签发，不要复制旧 token 或把签名 URL 写进工单。

原 SDK 实际发送：

```json
{"sequence":0,"cmd":"speed","rate":2}
```

16 倍只将 rate 改为数值 16。每个对照使用全新会话，不把上一轮播放状态混入。

## 实际与预期

| 指令 | 实际 | 预期 |
| --- | --- | --- |
| speed / rate=2 | 成功回复后，录像从约 10:00:08 回到约 09:49 的旧位置，再从旧位置推进。WASM 录像时间与解码画面左上角时间都能确认。 | 保持当前录像落点，从该点按约 2 倍推进。 |
| speed / rate=16 | 成功回复后，持续约 34 秒，录像只推进约 34 秒，仍约 1 倍。 | 按约 16 倍推进；若不支持，应明确返回不支持，不能只返回 OK。 |

独立原 SDK 对照仅有一条媒体连接，候选播放器已停止。它没有二壮新增的倍率测量、自动恢复、光标过滤或软件解码选择，因此不能仅通过改前端验证阈值解决上述输出问题。

已排除：按钮过早发送（普通播放稳定十余秒再发送仍复现）；仅显示时间解析错误（原始画面时间也回退）；候选自动发送 speed1（没有）；把 ACK 当实际倍率（验收依据是画面时间推进）。

## 请设备取流负责人补齐

补充对照：完整厂商 JSPlugin / PlayCtrl 使用独立 Decoder.wasm，经适配连接同一测试取流地址。确认每轮只有一个 client，CDP 各记录一条 speed 指令。2 倍从 `10:00:37.593` 倒退至 `09:49`，画面截图可确认；16 倍在 34.192 秒内仅推进 32.283 秒。这进一步表明不能仅通过替换二壮解码组件解决当前异常，但不等同于直连 NVR 测试，也不能断言设备硬件最高倍率。

1. 当前实际部署的 `/nvrapi/ws` 是否原样转发 speed；若有包装，提供 speed 处理函数及设备 API 的参数换算。已有 nvr-proxy 示例只有消息转发，未包含这一实现。
2. 该 NVR 对数值倍率 2/4/8/16 的支持范围、失败如何返回；`statusString=OK` 是收到指令还是设备已执行成功。
3. 切速保持当前录像位置是否需要额外定位/抽帧控制；若需要，提供此 WebSocket 服务实际支持的字段、时间格式、控制顺序和成功样例。通用 SDK 的 seek 字段不能未经验证直接沿用。

不是要求重新提供同一份前端 setSpeed 封装。现有封装和 JSON 已对照运行，缺的是当前部署链路与设备控制的实际契约。

## 二壮已完成的独立修复

- ACK 和画面测速分开，六秒暂不能确认时保留流，不自动恢复普通速度。
- 实际解码帧绑定录像时间；暂停停止旧流，继续/恢复从观看位置重新签发。
- WASM 首包与初始化期间媒体数据按序缓存，加入容量上限和旧代次保护。
- 支持时选择软件低延迟 H.264 解码，修复稀疏帧在硬件路径积压的问题；实际配置失败可回退。

这些代码是本地 4.10.4 候选，尚未推送或部署。4/8 倍有实际加速片段，完整矩阵及 2/16 倍未通过，不能用前端单元测试替代设备验收。
