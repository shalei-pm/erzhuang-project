# UI Standards

本文件是二壮项目的前端 UI 基准。目标不是做炫，而是让门店空间资源管理系统看起来像成熟、可靠、可长期维护的企业后台。

## 1. 产品气质

- 定位：轻量企业后台 / SaaS admin。
- 关键词：清楚、克制、稳定、信息密度适中、操作路径短。
- 避免：营销页式大 hero、装饰性渐变、无意义大卡片堆叠、过度圆角、默认紫色科技风、AI 味插画。
- 可参考方向：Ant Design、Arco Design、Semi Design 的后台信息层级和控件克制感。

## 2. 布局原则

- 首屏优先展示真实业务工作台，不做宣传型首页。
- 页面结构以列表、详情、弹窗、Tab、表格、表单、状态反馈为主。
- 列表页优先支持扫描：关键字段对齐，操作列稳定，不因文案换行挤压。
- 详情页只读信息用陈列展示，不做成输入框样式。
- 弹窗用于强任务流，尺寸要足够承载内容，但不压迫浏览器边缘。

## 3. 视觉 Token

所有颜色、字号、圆角、阴影优先从 `frontend/src/styles.css` 的 `:root` token 调整。

- 主色：用于主按钮、关键选中态、重点信息。
- 文本：至少区分主文本、次文本、弱提示文本。
- 背景：页面背景、内容面、浅色提示面分层。
- 边框：默认细边框，避免重描边。
- 圆角：后台卡片和控件默认不超过 8px，图标按钮保持稳定方形尺寸。
- 阴影：只用于浮层、弹窗、悬浮预览、当前选中状态，避免全页面漂浮感。

## 4. 按钮规范

- 主操作：页面或弹窗里的最高优先级动作，例如“添加门店”“保存”“创建门店”。
- 普通操作：编辑、删除、扫描、识别、上移、下移。
- 轻操作：关闭、增加一行、收起展开，优先使用图标按钮。
- 危险操作：删除类按钮需要有颜色区分和二次确认，不和普通操作混淆。
- 同一区域内按钮字号、行高、间距必须统一。

## 5. 表格规范

- 表头清晰、字段顺序稳定。
- 操作列固定右侧，按钮不纵向挤压。
- 数量类字段居中或右对齐，文本类字段左对齐。
- 空值统一显示 `-`。
- 状态使用标签，不只依赖颜色表达。
- 搜索后无结果需要有明确空态，不让用户以为系统卡住。

## 6. 弹窗规范

- 标题说明当前任务，不写长篇说明。
- 右上角关闭按钮使用稳定图标按钮样式，不能变形。
- 底部操作保持“取消 / 主操作”清晰分组。
- 有未保存修改时，关闭前需要确认。
- 表单错误应靠近对应区域，必要时顶部给整体提示。

## 7. 表单规范

- 可编辑信息使用输入框、选择框、上传控件。
- 不可编辑信息只读展示，不伪装成表单。
- 必填项保存时统一校验，错误文案要告诉用户怎么修。
- 后端字段级错误必须透传成用户能理解的中文，不允许只显示 `validation failed`。

## 8. 交互状态

每个可交互元素至少考虑：

- 默认态
- hover 态
- focus 态
- disabled 态
- loading 态
- error 态
- selected 态

focus 态不能丑，但也不能完全消失；键盘可访问性后续要逐步补齐。

## 9. 设计图标注

- 区域颜色保持业务一致：
  - 治疗室：红色系
  - 面诊室：绿色系
  - 生美：蓝色系
- 未选中区域以边框为主，减少大面积底色干扰。
- 选中区域在同色系里加深边框、阴影或底色，不切换成其他颜色。
- 右侧区域卡片和左侧矩形框必须能互相定位。

## 10. 版本和验收

- 页面底部必须展示版本号。
- 用户反馈 UI 问题时，优先记录页面版本号和 Git commit。
- 前端改动发布前必须做真实浏览器验收，不能只看构建通过。
